## Purpose

How the pool protocol's four messages ride ricochet: which folder submissions go to, where replies go, how the descriptor and announcements are published, how the server's identity is kept, and what the transport's limits mean for the pool.

## ADDED Requirements

### Requirement: Folders and payloads
A wallet SHALL send a submission as one message whose payload is the `pool-protocol` submission bytes, to the coordinator's peer id, in the folder `pool/submissions`, persistent, and encrypted to the coordinator's identity. The coordinator SHALL send a reply as one message whose payload is the reply bytes, to the sender's peer id, in the folder `pool/replies`, persistent and encrypted. No other folder SHALL be read or written by the pool.

#### Scenario: A submission arrives where the server reads
- **WHEN** a wallet sends a submission to `pool/submissions`
- **THEN** the server's next drain returns it with the wallet's peer id as sender and the submission bytes as payload

#### Scenario: A reply arrives where the wallet reads
- **WHEN** the server answers a submission
- **THEN** the wallet's `pool/replies` folder holds one message whose payload decodes to a reply with the submission's id

### Requirement: The pool's feed
The coordinator SHALL publish one public feed at `pool/rounds` under its own peer id, whose first entry is the pool's descriptor bytes and whose every later entry is one announcement's bytes, in round order, with no other entry kind. A wallet SHALL read the feed by sequence from where it last stopped, and SHALL treat an entry that does not decode as the end of what it can use.

#### Scenario: Descriptor first
- **WHEN** a pool is created
- **THEN** the feed's entry at sequence 1 decodes to a descriptor whose txids are the pool's genesis

#### Scenario: Announcements in order
- **WHEN** two rounds have been published
- **THEN** entries 2 and 3 decode to announcements for rounds 1 and 2

#### Scenario: Reading from a sequence
- **WHEN** a wallet asks for entries from sequence 3
- **THEN** it receives round 2's announcement and whatever came after, and nothing before

### Requirement: Identity
The coordinator's ricochet identity SHALL be an Ed25519 seed kept in the identity file the configuration names, created on `create` and never regenerated by `run`; its peer id is what the descriptor's readers address. The identity file SHALL be readable by the owner only.

#### Scenario: The same peer id across restarts
- **WHEN** the server is restarted
- **THEN** its peer id is the one the feed was created under, and a wallet's submission to it is answered

### Requirement: Delivery and limits
The server SHALL mark every consumed message delivered, since a mailbox holds at most 1,000 undelivered messages; SHALL send nothing over the transport's 10 MB frame (a submission is under 128 KB and every other message under 4 KB by `pool-protocol`); and SHALL retry a send that the client reports as failed up to a configured count before recording it in the status.

#### Scenario: A thousand submissions
- **WHEN** 1,000 submissions arrive before the server drains
- **THEN** all are consumed over successive drains and the folder is empty afterwards

#### Scenario: A reply that cannot be sent
- **WHEN** the ricochet server is unreachable when a reply is due
- **THEN** the reply is retried the configured number of times and the failure, with the submission id, is in the status

### Requirement: What the transport reveals
The server SHALL use one peer id for the pool and address replies only to the sender; it SHALL put nothing per transfer on the feed. The ricochet server sees who sent what when: a wallet that wants unlinkable submissions uses a fresh peer id per submission, which this transport accepts since it keys nothing on the sender.

#### Scenario: A fresh sender per submission
- **WHEN** two submissions arrive from two peer ids the server has never seen
- **THEN** both are answered to their own peer ids

### Requirement: Hostile senders
Any peer can write to the folder. The server SHALL accept a message from any sender, SHALL decode its payload as the library does (bounded, refusing with a named reason), and SHALL keep no state for a sender.

#### Scenario: Random bytes in a message
- **WHEN** 100 messages of random bytes are sent to the folder
- **THEN** each is marked delivered, at most a malformed reply is sent for those with a readable id, and the server is unaffected
